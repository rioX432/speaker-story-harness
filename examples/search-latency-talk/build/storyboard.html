課題から技術選択に至る論理

C1 どこが遅いかを測ってから選ぶ
  • LIKE検索で始める構成は小規模では妥当
  • 遅さはクエリ・整形・転送に分かれて現れうる
  • 既存DBの改善（インデックス・取得列）を先に試す
  • それでも残る遅さに対して、転置インデックスが効くかを仮説として立てる
  • 同じ結果を返す条件で、処理ごとに分けて測る
C2 インデックスの設計から選ぶ
  • 検索要件を4つに分ける
  • 各要件で B-tree が得意なことと苦手なことを示す
  • 苦手な要件に対する転置インデックスの仕組みを示す
  • 要件と構造の対応表で選ぶ
C3 速くなるはずが、速くならなかった
  • 検索エンジンで速くなるという期待を示す
  • 検索単体で比べると期待どおり短い
  • 応答全体で比べると差が小さい
  • 差が消えた理由を処理ごとに分解する

重要な発見

C1 どこが遅いかを測ってから選ぶ
  • 既存DBの改善だけで応答時間が大きく下がる（仮の値）
  • 検索単体ではエンジンが短いが、応答全体では差が小さい（仮の値）
C2 インデックスの設計から選ぶ
  • 語の一致と関連度の並べ替えは、B-tree の LIKE では表しにくい
C3 速くなるはずが、速くならなかった
  • 検索単体の差が応答全体では小さくなる（仮の値）

    理由: B2 の課題は仮説（E2）で、B7 の測定は架空の1台の環境（E7）。課題で挙げた「整形と転送」は測っているが、実環境の遅さとは対応していない

    修正案: B2 を「データが増えた場合のシナリオ」と明示し、B7 の測定の終点を B2 の分解と同じ3つにそろえる

  4. 実験の結果から技術選択の結論が導けるか
    満たす

    理由: B7 の「応答全体では差が小さい」から、B8 の「応答全体で利益が残るときに選ぶ」が導ける

  5. 冒頭の問いに最後までに答えているか
    満たす

    理由: B8 が冒頭の問い（エンジンで本当に速くなるか）に「既定路線ではない」と答えている

  6. 各章の順番を入れ替えると論証が崩れるか
    満たす

    理由: B3 と B4 を入れ替えると、既存DBの改善より先に新しい技術が出て解決策ありきになる。B6 と B7 を入れ替えると、数値の前提が後から出る
